# Maskarad — дизайн модуля безопасности персональных данных

Статус: реализовано (см. README.md, docs/quality.md, docs/performance.md). Дата: 2026-09-22; §4.3, §10 и §12 уточнены 2026-09-23 по итогам нагрузочного прогона на проде.

## 1. Что строим и зачем

Прокси-модуль в цепочке **система-потребитель → Maskarad → LLM → Maskarad → система-потребитель**.
На входе — текст запроса к LLM; модуль находит персональные данные (ПДн), маскирует их,
отдаёт «безопасный» текст модели, а ответ модели демаскирует обратно. Правила, набор типов ПДн,
стиль маски и право на демаскирование настраиваются **на систему-потребителя**, без правки кода.

Одновременно модуль реализует контракт автопроверки `POST /process`
(маскирование/демаскирование, коррелируемые по `payload_id`).

## 2. Что в ТЗ определяет дизайн

| Факт из ТЗ | Следствие для дизайна |
|---|---|
| Метрика автопроверки — нормированный span-based Левенштейн против **эталонной маски** | Вид маски — не деталь, а оцениваемый результат. Стиль маски на каждый тип ПДн задаётся конфигом («стратегия маскирования»), чтобы подогнать под эталон без правки кода. Ориентир из контракта: `Иванов Иван Иванович` → `И. И. И.`, `4509 123456` → `45** ****56`. |
| `/process` без авторизации: только `{payload, payload_id}` | Нужен «анонимный» профиль системы по умолчанию для `/process`; остальные эндпоинты — только по ключу из allowlist. |
| Второй запрос с тем же `payload_id` = демаскирование; ретраи до 3 попыток; таймаут 10 с | Идемпотентность: по `payload_id` храним и маску, и соответствие. Повтор первого запроса (payload == оригинал) снова вернёт маску, а не попытается демаскировать. |
| Несколько реплик в Kubernetes | Соответствия хранятся в Redis (общем для реплик); память процесса — L1-кэш, который заполняется только после подтверждённой записи в Redis. Самостоятельным хранилищем память бывает лишь при `backend: memory` и у реплики, стартовавшей без Redis (она помечается `degraded`). |
| RPS 1000 (цель 2000) при latency ≤ 0.5–1 с, тексты до 100 000 токенов | Горячий путь — детерминированный и без ML: regex + автоматы Aho-Corasick по словарям + валидаторы. Rust: один проход по тексту в единицы миллисекунд, 2000+ RPS на 4 ядрах. ML-NER — опциональный плагин. |
| Ловушки: «поэт Александр Пушкин», «адрес отделения Банка» | Отдельный слой «принадлежность к ПДн»: контекстные слова-подавители, справочники публичных персон и публичных адресов, правила комбинаций. |
| 13 из 30 баллов — за качество детекции/маскирования/демаскирования; 4–5 — за скорость | Основные усилия — в детекторы, golden-датасет и метрику качества; производительность закрывается выбором Rust и архитектурой. |
| «Никаких утечек в логи/метрики» | Тип-обёртка `Sensitive<T>` без `Display`/`Debug` сырого значения; в логах — только типы, количества, длины, хэши. |

## 4. Конвейер обработки

### 4.1. Маскирование
1. **Normalize.** Unicode NFC; строится lower-case копия текста с картой смещений «lower-байт → оригинальный байт» (у кириллицы длина в UTF-8 при смене регистра не меняется, но карта делает алгоритм корректным для любого Unicode). Все детекторы работают по lower-копии → **регистронезависимость гарантирована конструктивно**, а спаны отображаются в оригинал.
2. **Detect.** Каждый детектор возвращает `Candidate { span, pii_type, confidence, evidence }`. Три семейства:
   - *Pattern*: скомпилированные `regex` (один `RegexSet` как префильтр, затем точные `Regex` только для сработавших) + валидатор (Luhn, контрольные суммы ИНН/СНИЛС, валидность даты, диапазоны).
   - *Gazetteer*: один автомат `aho-corasick` (leftmost-longest) на все словари сразу (имена, фамилии, города, страны, публичные персоны…); результат — совпадения с классом словаря.
   - *Composite*: сборка сложных сущностей из соседних кандидатов/токенов (ФИО из фамилия+имя+отчество; адрес из индекса, города, улицы, дома, квартиры; «серия … номер …»).
3. **Resolve.** Единый резолвер поверх всех кандидатов:
   - контекстные усилители/подавители (окно N символов до/после: «паспорт», «выдан», «CVV», «поэт», «отделение банка»…);
   - справочники-исключения (публичные персоны, публичные адреса, корпоративные телефоны/e-mail);
   - правила комбинаций (например, `PIN` маскируется только при наличии `CARD_NUMBER` в тексте — настраивается);
   - пороги уверенности на тип, включённость типа для данной системы;
   - разрешение пересечений: приоритет по силе валидатора и типу (CARD > PHONE > INN для цифровых строк; ADDRESS-компонент побеждает FIO внутри «ул. Пушкина»), затем «длиннее лучше».
4. **Mask.** Для каждой финальной сущности — стратегия из профиля системы (см. §7). Результат: `masked_text` + `entries[] = {pii_type, mask, original, start, end}`.
5. **Store.** В хранилище по ключу `(system_id, payload_id)` кладутся `entries` (оригиналы зашифрованы) и хэш маскированного текста. Сам оригинальный текст **целиком не хранится** — он восстанавливается подстановкой (минимизация данных).

Маска — **чистая функция** от `(текст, конфиг системы)`: детерминированные номера плейсхолдеров по порядку в тексте. Поэтому при сбое записи в Redis `/process` может ответить `429 STORE_BUSY`, а ретрай — хоть на другой реплике — даст ту же маску; и поэтому же запись, которую успел создать параллельный ретрай (`SET NX` → «уже есть»), равна нашей.

### 4.2. Демаскирование
Вход: текст + `(system_id, payload_id)`. Из хранилища берутся `entries`.
- Быстрый путь: если хэш входа совпадает с хэшем сохранённой маски — подставляем оригиналы по сохранённым позициям (ровно то, чего ждёт проверяющая система; «местоположение знаков» сохраняется по построению).
- Общий путь (ответ LLM, где текст переписан): для каждой записи (сначала самые длинные маски) ищем вхождения маски в тексте и подставляем оригинал; при одинаковых масках (два `45** ****56`) — по порядку появления. Для профиля с плейсхолдерами (`<PER_1>`) подстановка однозначна — это и есть аргумент за плейсхолдеры в LLM-сценарии.
- Если система лишена права демаскирования — `403` с понятным сообщением.

### 4.3. Идемпотентность `/process`
Для пары запросов с одним `payload_id`:

| Состояние по `payload_id` | payload | Действие |
|---|---|---|
| нет записи | любой | маскирование, сохранить |
| есть запись | == оригиналу (хэш) | ретрай первого шага → вернуть ту же маску |
| есть запись | == маске (хэш) | демаскирование (быстрый путь) |
| есть запись | иное | демаскирование общим путём (текст изменён LLM) |
| хранилище не ответило (чтение или запись) | любой | `429 STORE_BUSY` + `Retry-After: 1`: направление не угадывается, маска вместо оригинала не выдаётся, проверяющая система повторяет запрос |

## 6. «Принадлежность к ПДн»: как не маскировать лишнее

Четыре механизма, все — конфигурируемые:
1. **Контекст-подавители** (слова перед/после сущности): «поэт», «писатель», «композитор», «актёр», «режиссёр», «учёный», «император», «президент», «полководец», «философ», «святой», «имени» (для ФИО); «отделение», «офис», «филиал», «банкомат», «головной офис», «ДО №» (для адресов); «горячая линия», «служба поддержки» (для телефонов).
2. **Справочники-исключения**: публичные персоны (встроенный список + пользовательский), публичные адреса и телефоны организации, корпоративные e-mail-домены. Совпадение — регистронезависимое, с учётом падежных форм (сравнение по основе/через включённые формы).
3. **Требование контекста для «слабых» типов**: CVV, PIN, код подразделения, одиночное имя, голая дата, город — сами по себе не ПДн.
4. **Правила комбинаций** (per-system): `mask X only if any of [Y, Z] present in text/sentence` — например, `PIN ⇐ CARD_NUMBER`, `DATE ⇐ FIO|PASSPORT`, `ADDRESS_CITY ⇐ ADDRESS_STREET|BIRTH_PLACE ctx`.

Выбор по умолчанию для профиля автопроверки — **максимальная полнота**: комбинации не требуются для «сильных» типов, для «слабых» — контекст. Рациональное обоснование: в ТЗ систематические пропуски караются сильнее ложных срабатываний, а датасет построен вокруг категорий ПДн (в предложениях есть контекст).

## 7. Стратегии маскирования и профили систем

Стратегия — параметризованный алгоритм, назначаемый на тип ПДн в **профиле** системы:

| Стратегия | Пример | Назначение |
|---|---|---|
| `initials` | `Иванов Иван Иванович` → `И. И. И.` | эталон автопроверки для ФИО |
| `partial{keep_start, keep_end, fill}` | `4509 123456` → `45** ****56` | эталон для номеров; нецифровые символы (пробелы, дефисы, скобки) сохраняются на местах |
| `full{fill}` | `ivanov@mail.ru` → `**************` | позиционно-сохраняющая маска |
| `placeholder{template}` | `<PER_1>`, `[CARD_2]` | LLM-сценарий: однозначное демаскирование ответа модели, смысл запроса для модели сохраняется |
| `synthetic` | `Иванов Иван Иванович` → `Петров Сергей Николаевич`; карта → Luhn-валидный фейк | «замена синтетикой»: модель видит правдоподобный текст |
| `token{prefix}` | `tok_9f2a…` (HMAC-хэш) | токенизация: стабильный токен для одного и того же значения в рамках payload |
| `remove` | `` | удаление |

Встроенные профили: `reference` (эталон автопроверки: `initials` для ФИО/держателя, `partial` для номеров, `full` для остального), `placeholder` (для LLM-интеграций), `synthetic`. Профиль можно переопределять потипово.

Открытый вопрос (§20): точный эталонный вид маски для каждого типа неизвестен — стратегия по умолчанию подгоняется по результатам пробы эталонного эндпоинта.

## 8. Модель конфигурации

Один YAML (плюс файлы словарей), hot-reload по изменению файла/`POST /admin/reload`; при ошибке валидации остаётся последняя рабочая версия.

```yaml
server:
  listen: 0.0.0.0:8080
  max_body_bytes: 4194304          # 4 MiB ≈ 1 млн символов, с запасом под 100k токенов
  max_inflight: 2048                # потолок одновременных запросов, все полосы допуска; выше — 429
  request_timeout_ms: 8000
  admission: { enabled: true, min_limit: 8, target_ms: 5 }   # адаптивный допуск, §12.1; large_limit — по числу CPU

store:
  backend: redis                    # redis | memory
  redis_url: ${REDIS_URL}
  ttl_seconds: 3600
  encryption_key: ${MASKARAD_STORE_KEY}   # 32 байта base64, AES-256-GCM
  memory_fallback: true             # только на старте без Redis: реплика на памяти, degraded
  timeout_ms: 1000                  # таймаут команды Redis; один повтор после таймаута
  memory_capacity_bytes: 268435456  # L1-кэш / память процесса, лимит в байтах (256 MiB)

llm:
  base_url: ${LLM_BASE_URL}         # любой OpenAI-совместимый API
  api_key: ${LLM_API_KEY}
  timeout_ms: 60000

pii_types:                          # встроенные типы + расширения; секция может быть в отдельном файле
  - id: EMPLOYEE_ID                 # пример расширения без кода
    kind: pattern
    patterns: ["\\bemp-\\d{6}\\b"]
    context: { before: ["табельный", "сотрудник"], window: 30, required: false }
    validator: none
    default_strategy: placeholder

allowlists:
  public_persons_file: data/public_persons.txt
  public_addresses: ["г. Москва, ул. Каланчёвская, д. 27"]
  public_phones: ["8 800 200-00-00"]
  corporate_email_domains: ["alfabank.ru"]

systems:
  - id: alfasonar                   # проверяющая система: без ключа, только /process
    enabled: true
    auth: anonymous
    pii_types: all
    demask: true
    profile: reference
  - id: support-chatbot
    enabled: true
    auth: { api_keys: ["sha256:…"] }
    pii_types: [FIO, PHONE, EMAIL, CARD_NUMBER, CVV, PIN, ADDRESS]
    demask: true
    profile: placeholder
    overrides: { CARD_NUMBER: { strategy: partial, keep_start: 4, keep_end: 4 } }
    combination_rules:
      - { mask: PIN, only_if_present: [CARD_NUMBER] }
  - id: analytics-batch
    enabled: false                  # выключена — 403
    auth: { api_keys: ["sha256:…"] }
    pii_types: all
    demask: false                   # демаскирование запрещено
    profile: synthetic
```

**Краткая инструкция по настройке (≤5 предложений, пойдёт в README):** Все настройки — в `config/maskarad.yaml`. Чтобы подключить систему-потребителя, добавьте запись в `systems` с её `id`, ключом (`api_keys`), списком типов ПДн (`pii_types`), флагом `demask` и профилем маскирования (`profile`); `enabled: false` отключает доступ. Новый тип ПДн добавляется записью в `pii_types` (регулярное выражение, контекст, валидатор, стратегия) без правки кода. Ловушки (публичные персоны, адреса отделений, корпоративные телефоны) — в `allowlists`. Конфиг перечитывается на лету; ошибочный файл не применяется, действует предыдущий.

## 9. API

| Метод | Назначение | Авторизация |
|---|---|---|
| `POST /process` | Контракт автопроверки: `{payload, payload_id}` → `{result}`; направление по состоянию `payload_id` (§4.3) | анонимный профиль (настраивается) или `X-API-Key` |
| `POST /v1/mask` | `{text, payload_id?}` → `{masked, payload_id, entities:[{type,start,end,mask}]}` | `X-API-Key` |
| `POST /v1/demask` | `{text, payload_id}` → `{text}` | `X-API-Key`, система с `demask: true` |
| `POST /v1/detect` | `{text}` → сущности без маскирования (dry-run, UI) | `X-API-Key` |
| `POST /v1/chat/completions` | OpenAI-совместимый прокси: маскирует `messages[].content`, шлёт в upstream, демаскирует `choices[]` (в т.ч. SSE-стриминг с буферизацией на границах плейсхолдеров) | `X-API-Key` (или `Authorization: Bearer <key>`) |
| `GET /healthz`, `GET /readyz` | liveness / readiness (readiness учитывает Redis, но переходит в `degraded`, а не в `down`) | — |
| `GET /metrics` | Prometheus | внутренняя сеть |
| `POST /admin/reload` | перечитать конфиг | админ-ключ |
| `GET /` | Web UI для демо | — (UI сам ходит по API с ключом) |

Ошибки — единый формат `{"error": {"code": "STORE_UNAVAILABLE", "message": "…", "request_id": "…"}}`; коды: `INVALID_REQUEST` (400), `UNAUTHORIZED` (401), `SYSTEM_DISABLED`/`DEMASK_FORBIDDEN` (403), `MAPPING_NOT_FOUND` (404), `RATE_LIMITED` (429 + `Retry-After`), `STORE_BUSY` (429 + `Retry-After: 1`, только `/process`: хранилище не ответило, запрос повторяется), `STORE_UNAVAILABLE` (503, `/v1/*`), `LLM_UNAVAILABLE` (502/504). Ответы, которые дал не обработчик, идут не в едином формате, и `request_id` у них только в `X-Request-Id`: `413` (тело больше `server.max_body_bytes`, текст от axum), `503` по `server.request_timeout_ms`, `404` и `405` роутера (пустое тело).

## 10. Хранилище соответствий

- Ключ: `mk:{system_id}:{sha256(payload_id)}` — сам `payload_id` в Redis не хранится.
- Значение: `AES-256-GCM(entries + masked_hash + original_hash)`; nonce случайный, ключ — из Secret. Redis видит только шифртекст.
- TTL по конфигу (по умолчанию 1 ч); `SET … NX EX` — одна операция на маскирование, `GET` — одна на демаскирование. Запись только создаётся: если ключ уже есть (параллельный ретрай или повтор команды после таймаута, когда Redis её уже применил), хранилище отвечает «уже есть» — это успех, а не ошибка, и существующая запись не перезаписывается. Одно мультиплексированное соединение на реплику; таймаут команды `store.timeout_ms` (1 с), после таймаута — один повтор, второй таймаут или ошибка Redis возвращаются вызывающему.
- L1-кэш: локальный `moka`-кэш с тем же TTL, ограниченный по байтам (`store.memory_capacity_bytes`, 256 MiB; вес записи — ключ, хэши и все сущности с оригиналами). Заполняется **после** подтверждённой записи в Redis и при чтении из Redis; демаскирование, пришедшее на ту же реплику, обходится без Redis.
- Ошибка Redis никогда не маскируется памятью: `/process` отвечает `429 STORE_BUSY` (§4.3), `/v1/*` — `503 STORE_UNAVAILABLE`; метрика `maskarad_store_degraded=1`, заголовок `X-Maskarad-Degraded: store`, `readyz` → `degraded`. При восстановлении Redis — обычный режим без ручных действий.
- Память как единственное хранилище — только `backend: memory` и, при `memory_fallback: true`, реплика, для которой Redis был недоступен на старте: она работает, но с первого запроса помечена `degraded`, потому что её соответствия невидимы другим репликам.
- Отвергнутый вариант (был реализован до 2026-09-23): запись сначала в память, при ошибке Redis — `Ok`. На проде это давало соответствие, видимое одной реплике: соседние отвечали на демаскирование маской, а ошибка чтения трактовалась как «записи нет» и перезаписывала соответствие.
- Альтернатива, которую сознательно не берём: sticky-роутинг по `payload_id` на ingress — проще, но привязывает корректность к балансировщику.

## 11. Безопасность, логи, метрики

- **Allowlist систем**: ключи хранятся хэшированными (SHA-256) в конфиге, сырые — в Secret/переменных окружения; `enabled: false` — мгновенное отключение. mTLS/сетевые политики — на уровне ingress (документируем).
- **Никаких ПДн в логах/метриках — конструктивно.** Все значения сущностей живут в `Sensitive<String>`: `Display` нет, `Debug` печатает `[REDACTED]`, прозрачный `Serialize` нужен только для записи соответствия, которая уходит в хранилище зашифрованной. В лог не пишутся тело запроса, текст ответа, сырой `payload_id` и поле `message` ошибок API — только хэши, счётчики и коды. Паники: `logging::install_panic_hook` заменяет стандартный обработчик и пишет одну строку ERROR `panic` с `panic_location`, без сообщения. Сообщение паники может цитировать текст: срез `&str` не по границе символа на Rust 1.94 печатает до 256 байт строки, на 1.98 — символ на границе; стандартный обработчик выводит его в stderr, а stderr контейнера попадает в хранилище логов так же, как stdout. По той же причине у упавшей задачи маскирования в blocking-пуле в лог идут только `panicked` и `cancelled`, а не `JoinError`, чей `Display` содержит сообщение паники.
- **Лог запросов** — stdout, JSON (`MASKARAD_LOG_FORMAT=pretty` — читаемый вид), ровно одна строка на каждый запрос к `/process`, `/v1/mask`, `/v1/demask`, `/v1/detect` и `/v1/chat/completions`, включая отказы, и на запрос по неизвестному пути. В каждой строке есть `request_id` (тот же, что в заголовке ответа `X-Request-Id` и в теле ошибки API), `route` и, кроме `request panicked`, `status`; `route` — шаблон маршрута, а не URI от клиента, у неизвестного пути — `unmatched`, сам путь в лог не попадает. У строк обработчиков `duration_ms` — время от входа в обработчик (тело запроса к этому моменту уже прочитано) до готового результата, с шагом 0,01 мс: запрос к `/process` на короткий текст занимает десятые доли миллисекунды, и целые миллисекунды давали бы 0. Это же значение записывается в `maskarad_request_duration_seconds`, поэтому лог и метрика не расходятся; сериализация ответа и запись самой строки лога не входят ни туда, ни туда.

  | `message` | Маршруты | Поля, кроме `request_id`, `route`, `status`, `duration_ms` |
  |---|---|---|
  | `masked` | `/process`, `/v1/mask` | `system`, `payload_id_hash` (первые 12 hex SHA-256), `text_bytes`, `tokens`, `entities`, `types` (`FIO:1,PASSPORT:1`); на `/process` ещё `direction=mask`, `store`, `degraded` |
  | `masked (retry)` | `/process` | `direction=mask_retry`, `system`, `payload_id_hash` |
  | `demasked` | `/process`, `/v1/demask` | `system`, `payload_id_hash`, `entries`; на `/process` ещё `direction` (`demask_exact` / `demask_substitute`), `text_bytes`, `tokens`; на `/v1/demask` — `exact` |
  | `detected` | `/v1/detect` | `system`, `text_bytes`, `entities` |
  | `proxied` | `/v1/chat/completions` | `system`, `payload_id_hash`, `tokens_in`, `tokens_out`, `entities`, `types`, `demasked` |
  | `request rejected`, `proxy request rejected` | все пять | `code` — код ошибки API (§9), уровень WARN |
  | `request rejected` без `code` | все пять, `unmatched` | только общие; `413`, `503` по таймауту, `404`, `405`, уровень WARN |
  | `request aborted` | все пять | только общие, `status=499`: клиент закрыл соединение до ответа, уровень WARN |
  | `request panicked` | все пять | `request_id`, `route`, `duration_ms`, без `status`: обработчик запаниковал, ответа нет, уровень ERROR |

  Отказ допуска при перегрузке (`429 RATE_LIMITED`, §12.1) пишет `limits::admit` ещё до обработчика: строка `request rejected` с `code`, `reason` (`adaptive_limit` — адаптивный лимит коротких запросов при нехватке CPU, `large_lane_full` — большой текст не дождался своей полосы, `inflight_limit` — потолок `server.max_inflight`) и без `duration_ms`, потому что обработка не начиналась. Перед отказом `STORE_BUSY` идёт отдельная строка WARN с тем же `request_id` и текстом ошибки хранилища.

  Ответы, которые дал не обработчик, логирует `logging::log_unlogged` — внешний слой API-роутера, снаружи лимита тела и таймаута: `413` (экстрактор тела отклоняет запрос до входа в обработчик), `503` по `server.request_timeout_ms` (`TimeoutLayer` сбрасывает future обработчика вместе с его ещё не записанной строкой), `405` и `404` роутера. Строка — `request rejected` без `code`; `duration_ms` в ней считается от входа в этот слой и включает чтение тела и ожидание таймаута; новый `request_id` уходит в `X-Request-Id` ответа. Обработчики и `limits::admit` помечают свои ответы расширением `logging::RequestLogged`, такие ответы слой пропускает без работы — отсюда ровно одна строка на запрос. Неизвестный путь обслуживает fallback API-роутера, поэтому он проходит через этот слой, но не через лимиты. Служебные маршруты (`/healthz`, `/readyz`, `/metrics`, `/v1/systems`, `/v1/types`, `/v1/profiles`, `/admin/reload`, `/docs`, `/docs/openapi.json`, `/docs/openapi.yaml`, `/`) строку запроса не пишут и `X-Request-Id` не получают.

  Запрос без ответа тот же слой логирует из `Drop` guard'а `Pending`, который снимается, когда ответ получен. Future запроса сбрасывается недовыполненным в двух случаях: клиент закрыл соединение (hyper бросает future; проверено живым прогоном — без guard'а такой запрос не оставлял ни одной строки) и обработчик запаниковал (tokio бросает future при раскрутке стека, `std::thread::panicking()` это различает). Первый пишется как `request aborted` со `status=499` — так тот же запрос записывает nginx, второй — как ERROR `request panicked`, перед которым идёт строка `panic` от panic hook. Обработчик пишет свою строку в том же poll, в котором возвращает ответ, поэтому строка обработчика и `request aborted` у одного запроса не встречаются.
- **Метрики** (Prometheus): `maskarad_request_duration_seconds{route,system,direction}` (histogram → latency p50/p95/p99), `maskarad_requests_total{route,status}` (→ RPS), `maskarad_tokens_total{direction}` (→ TPS), `maskarad_pii_detected_total{type,system}`, `maskarad_stage_duration_seconds{stage}` (`detect_mask`, `detect`, `demask`, `store_get`, `store_put`, `llm`), `maskarad_inflight`, `maskarad_rejected_total{reason}`, `maskarad_admission_limit`, `maskarad_admission_rtt_seconds`, `maskarad_admission_rtt_noload_seconds`, `maskarad_admission_lag_seconds` (§12.1), `maskarad_store_ops_total{op,result}`, `maskarad_store_retries_total{op}`, `maskarad_store_degraded`, `maskarad_llm_requests_total{result}`. Отказы допуска считаются только в `maskarad_rejected_total{reason}`, в `maskarad_requests_total` и в гистограмму латентности они не попадают. `413`, `503` по таймауту, `404`, `405`, оборванные клиентом и запаниковавшие запросы не попадают ни в одну метрику запросов, их видно только в логе. Токены — быстрая аппроксимация: буквенно-цифровые последовательности плюс отдельные знаки препинания.
- **Минимизация данных**: хранятся только оригиналы найденных сущностей, зашифрованные, с TTL; исходный текст целиком не сохраняется; тело запроса не логируется.
- В репозитории нет ключей и реальных ПДн: датасеты — синтетические, ключи — только `.example`.

## 12. Надёжность и деградация

| Отказ | Поведение |
|---|---|
| Redis не отвечает | один повтор команды после таймаута; затем `/process` → `429 STORE_BUSY` + `Retry-After: 1` (ретрай проверяющей системы), `/v1/*` → `503 STORE_UNAVAILABLE`; демаскирование на реплике с записью в L1 работает; метрика и заголовок деградации, `readyz` → `degraded` |
| Ошибка чтения или записи хранилища на `/process` | `429 STORE_BUSY`, направление не угадывается — маска вместо оригинала не выдаётся; соответствие попадает в L1 только после подтверждения Redis |
| Redis недоступен при старте | `memory_fallback: true` — реплика на памяти процесса, сразу `degraded`; `false` — сервис не стартует |
| LLM upstream недоступен/таймаут | `502`/`504` с сообщением; простой circuit breaker (N ошибок подряд → fast-fail на T секунд), метрика |
| Перегрузка | `429 RATE_LIMITED` + `Retry-After: 1` сразу, без очереди внутри пода: при нехватке CPU — адаптивный лимит коротких запросов; большие тексты ждут своей полосы до половины `request_timeout_ms`; потолок `server.max_inflight` (§12.1); ретраи проверяющей системы это учитывают |
| Невалидный JSON / пустой payload / нет payload_id | `400` с перечислением полей |
| Неизвестная/выключенная система | `401`/`403` |
| Ошибка в конфиге при reload | остаётся предыдущая версия, ошибка в лог и в `/readyz` |
| Огромный текст | лимит тела (`413`); в пределах лимита — обработка в blocking-пуле, чтобы не блокировать reactor |
| Паника в детекторе | `catch_unwind` вокруг конвейера → `500` без утечки текста, счётчик ошибок |

Graceful shutdown (SIGTERM → дождаться in-flight, readiness → false), `preStop`-задержка в K8s.

### 12.1. Защита от перегрузки

Прогон на проде 2026-09-23 (4 узла × 2 vCPU, 4 пода): до ~5 000 запросов/с ingress p99 40 мс; выше узлы упираются в CPU, а статический `server.max_inflight = 2048` пускал всё. Очередь внутри пода росла до ~1 100 запросов, стадия `store_get` — с 0.45 до 460 мс, хотя Valkey отвечал за 5–21 мкс: запросы ждали CPU, а не хранилище. Ingress p99 — 2.5 с, таймауты store → `STORE_BUSY`, 681 пара не собралась за 3 попытки. Поэтому при нехватке CPU излишек коротких запросов отсекается на входе: сразу `429 RATE_LIMITED` с `Retry-After: 1` (проверяющая ретраит 429) вместо места в очереди.

Каждый запрос API попадает в полосу (`limits::admit`):

| Полоса | Запросы | Ограничение |
|---|---|---|
| короткие | `Content-Length` до `server.blocking_threshold_bytes` (64 КиБ) или без него | `max_inflight`; при нехватке CPU — адаптивный лимит от `admission.min_limit` до `max_inflight` |
| большие | тело больше порога | `admission.large_limit` в обработке одновременно (по умолчанию — число CPU процесса), остальные ждут очереди до половины `request_timeout_ms`, потом `429` |
| только потолок | `/v1/chat/completions` | своего нет |

`server.max_inflight` (2048) — потолок всех полос вместе, ждущие большие тексты тоже считаются; это защита по памяти, а не по задержке. Сигнал задержки дают только короткие запросы: текст 16× обрабатывается около секунды при любой нагрузке, LLM-вызов длится столько, сколько отвечает апстрим, и по ним лимит сжимался бы без всякой очереди. Большие тексты ждут очереди, а не получают `429`: им нужна пропускная способность, каждый повтор стоит им секунду, а полоса нужна, чтобы они не заняли все ядра разом, — с этим справляется и очередь. Запрос без `Content-Length` считается коротким: за ingress-nginx заголовок есть всегда (тело буферизуется до проксирования), его шлют проверяющая, k6 и `maskarad bench`. Остаётся chunked-тело от прямого клиента, ограниченное `max_body_bytes`: один слот на несколько секунд и одна выборка из сотен в окне. Считать такие запросы большими значило бы ставить любой маленький chunked-запрос в очередь за большими текстами.

Тело отклонённого запроса дочитывается и выбрасывается до ответа (не дольше секунды). hyper оставляет соединение, только если запрос прочитан до конца, а после ответа сам читает ещё один раз — сколько принесёт одно чтение; остаток он не дочитывает и закрывает сокет, и клиент, который ещё пишет тело, получает reset вместо `429`. На ревью так пропадали отказы по текстам 455 КБ (`Broken pipe` у urllib и k6), за ingress-nginx это был бы `502`. Не дочитываются тело больше `max_body_bytes` (ему всё равно `413`), тело без `Content-Length` и тело клиента с `Expect: 100-continue`, который его ещё не отправлял. Цена при перегрузке не видна: при двукратной перегрузке с дочитыванием всех тел и только тел больше 8 КиБ число соединений, память и принятые запросы одинаковы (по два прогона).

**Когда включается лимит.** Фоновая задача раз в 5 мс меряет, сколько отдавший управление таск ждёт повторного запуска (`maskarad_admission_lag_seconds` — EWMA этого ожидания). Пока ожидание меньше 1 мс, CPU хватает, и короткие запросы ограничены только потолком: высокая задержка при свободном CPU — не своя очередь (например, хранилище не отвечает), меньше запросов ждать меньше не станут. Первая версия держала лимит всегда включённым с потолком 256, и пауза Valkey на 3.5 с при 625 запросах/с стоила 135–145 несобранных пар против 0 у статического 2048 (замер на ревью). Лимит включается, когда EWMA и три замера подряд не меньше 1 мс. Одиночная остановка хоста даёт один-два длинных замера, и включение по одной EWMA после такой остановки при 4 000 запросах/с (половина мощности ядра) отклонило 183 запроса: стартовое значение оказалось ниже очереди остановки — по всей видимости, потому что она ещё не вся попала в полосу. С тремя замерами тот же 30-секундный прогрев прошёл без отказов. Стартовое значение — вдвое больше запросов в полосе и не меньше `2 × rate_max × target` (см. ниже): при устойчивой перегрузке полоса заполняется за десятки миллисекунд и дальше работает градиент, а очередь, оставшаяся после остановки (хост забрал CPU, хранилище вернулось), рассасывается без отказов. Выключается лимит, когда EWMA секунду подряд ниже 0.5 мс: насыщенный CPU столько не простаивает. Уже через 50 мс свободного CPU включённый лимит держит место для вдвое большего числа запросов, чем в полосе: они ждут не CPU, а, например, вставшее хранилище, и пока ни один не завершился, пересчёта нет. Без этого тест с паузой хранилища время от времени падал под квотой CPU: пауза квоты включала лимит, пока полоса заполнялась, и остаток отклонялся до выключения.

**Как меняется.** Градиентный регулятор по образцу `GradientLimit` из Netflix concurrency-limits (`limits::gradient`). Раз в 100 мс:

```text
L_new  = L × clamp(target / rtt, 0.5, 1) + √L
L      = L + 0.5 × (L_new − L),  L ≥ rate_max × target,  min_limit ≤ L ≤ max_inflight
target = max(target_ms, min(2 × rtt_noload, 10 × target_ms))
```

Лимит двигается только в окне, где спрос не отставал от пропускной способности: полоса не уменьшилась больше, чем отклонила (пришло не меньше, чем завершилось). Рассасывающаяся очередь лимит не трогает, а если он при этом отказывает — растёт. Стоящая очередь (клиент с фиксированным числом одновременных запросов, генератор на своём лимите) и перегрузка, которую лимит отсекает, считаются. В таком окне лимит режется к цели, если ожидание запуска доходило до 0.5 мс, иначе растёт.

`rtt` — EWMA средних по окну: время короткого запроса от допуска до ответа. В выборку идут и `STORE_BUSY`: это `429` после таймаута хранилища и повтора, и при нехватке CPU это самые медленные запросы; остальные `4xx` обработчика — нет, они отвечают без работы, за задержкой которой следит лимит. `rtt_noload` — средняя задержка без своей очереди: минимум средних за 30–60 с по чистым окнам — лимит выключен, отказов нет, ожидание запуска всё окно ниже 0.5 мс. Первая версия брала любое окно, где ожидание в момент пересчёта было ниже 1 мс. При управляемой перегрузке оно держится у самого порога и время от времени проваливается под него; среднее такого окна, около цели, становилось базой, каждая ротация периода удваивала цель, и за две минуты лимит возвращался к потолку (замер на ревью: `rtt_noload` 0.16 → 26.6 мс, p99 маскирования 121 мс за 150 с перегрузки). Теперь перегрузка не даёт ни одного окна, а минимум ротируется только при новом наблюдении и доживает до её конца. Минимум отдельных выборок не годится: самый быстрый запрос `/process` — демаскирование из L1-кэша, а среднее обычной смеси без всякой очереди в разы больше. `target_ms` (5 мс) нужен потому, что короткий запрос без очереди занимает десятые доли миллисекунды: резать лимит на двойной такой задержке значило бы сбрасывать нагрузку, которую никто не замечает. Потолок цели в 10 × `target_ms` ограничивает ущерб от любой другой порчи базы: хранилище, которое отвечает дольше 25 мс, лимитом одновременных запросов не спрятать.

Ниже `rate_max × target` лимит не режется: `rate_max` — темп завершений в полосе с памятью в несколько секунд (−1 % за 100 мс, половина за 7 с: остановки исполнителя на стенде длились 2–3 с). По закону Литтла столько запросов в обработке при таком темпе ждут в своей очереди ровно `target`; если задержка всё равно выше, остальное не наше — исполнитель разбирает волну ретраев, которые надо отклонить, или хост на мгновение забрал CPU, и резать дальше значит только терять пропускную способность. Без этой границы сбой на несколько сотен миллисекунд опускал лимит с 67 до 9; он отрастал секунд десять, всё отклонённое за это время возвращалось ретраями, и p99 принятых запросов вырос с ~40 до 390 мс (замер на одном ядре при перегрузке в 1.75 раза). При обычной перегрузке CPU граница ниже точки, где сходится градиент, и ничего не меняет.

Отдельные выборки не обрезаются: у половины запросов `/process` (то же демаскирование из L1, один poll) время от очереди не зависит, и обрезка выборок по 2 × target держала среднее на цели, пока маскирование ждало 60 мс (замер `maskarad bench`, 10 000 запросов/с на одном ядре). Фильтруется среднее окна: в EWMA идёт меньшее из двух последних средних, не больше 2 × target, где градиент и так на нижней границе. Устойчивая очередь проходит без изменений. Без фильтра одно окно в 170 мс (хост на мгновение забрал CPU, на замере) за несколько следующих окон срезало лимит с 60 до 8; дальше он секунд десять отрастал, пока возвращались ретраи всего отклонённого за это время, и p99 принятых запросов вырос с 35 до 170–390 мс. Почему градиент, а не AIMD или Vegas: перегрузка здесь — очередь к CPU, задержка растёт с числом впущенных, и отношение цели к текущей задержке сразу говорит, сколько срезать. AIMD режет фиксированным шагом и медленнее выходит из перегрузки, Vegas оценивает очередь по тем же двум числам, но требует ещё порогов alpha/beta в запросах.

Горячий путь — несколько relaxed-атомиков без аллокаций: CAS счётчика полосы и потолка, `fetch_add` gauge `maskarad_inflight` (хэндл получен один раз, а не ищется в реестре на каждый запрос), одна `fetch_add` упакованной пары «число выборок, сумма». Пересчёт делает запрос, который первым завершился после конца интервала и выиграл CAS по времени, а не фоновая задача: пересчёт нужен именно при перегрузке, а таймерная задача ждала бы в той же очереди, что и защищаемые запросы. Включение и выключение делает проба под тем же мьютексом (`try_lock`, без ожидания). Слот освобождается в `Drop`: `TimeoutLayer` снаружи бросает future запроса по таймауту, в том числе пока большой текст ждёт своей полосы, и `maskarad_inflight` не уползает.

Чего допуск не делает. Отказ не бесплатен: `429` проходит тот же разбор HTTP, пишет строку лога и отвечает, и на замере стоит ~30 мкс CPU против ~70 мкс у обслуженного запроса из смеси `/process`. При перегрузке в разы отказы и их повторы занимают заметную долю CPU, и принятых запросов меньше, чем на потолке без отказов. `Retry-After` всегда `1`: так записано в контракте API, и проверяющая на это рассчитывает; повторы отклонённых возвращаются через секунду волной, и её допуск разбирает как обычную нагрузку. Ожидание до допуска (запрос прочитан из сокета, но ещё не дошёл до `limits::admit`) лимит не ограничивает, его видно только по `maskarad_admission_lag_seconds`. Замер до/после — в [docs/performance.md](performance.md#перегрузка-адаптивный-допуск).

Настройки — `server.admission` (`enabled`, `min_limit`, `large_limit`, `target_ms`), секция `server` читается при старте. `enabled: false` возвращает один статический лимит `max_inflight` с `reason=inflight_limit`, без полос и без ожидания больших текстов. Метрики — `maskarad_admission_limit` (при выключенном лимите равен `max_inflight`), `maskarad_admission_rtt_seconds`, `maskarad_admission_rtt_noload_seconds`, `maskarad_admission_lag_seconds`, отказы — `maskarad_rejected_total{reason}`; на дашборде — панель «Лимит допуска».

## 13. Производительность

Целевой уровень — **в 10 раз выше ТЗ: 10 000 RPS при latency в пределах SLA** (p99 ≤ 50 мс на типичных предложениях датасета), на одном узле с 4 ядрами; горизонтальное масштабирование репликами — сверх этого.

Бюджет CPU на запрос при 10k RPS на 4 ядрах — ~400 мкс на всё (HTTP, JSON, детекция, store), поэтому:
- детекция за один-два прохода по тексту: `RegexSet`-префильтр (одна DFA на все шаблоны, точные `Regex` — только для сработавших) + один автомат Aho-Corasick для многословных справочников; имена/фамилии — токенизация и hash-lookup лемм, а не автомат на 500k форм;
- ноль аллокаций в горячих циклах, буферы переиспользуются; `mimalloc`;
- Redis: одно мультиплексированное соединение на реплику с pipelining (Redis держит >100k ops/s), плюс локальный L1-кэш (moka, лимит в байтах) — демаскирование, пришедшее на ту же реплику, не ходит в Redis вовсе; запись в Redis завершается до ответа и до попадания в L1 (иначе демаскирование на другой реплике может опередить запись или не найти её);
- компиляция всех автоматов при старте (при reload — атомарная подмена `Arc`), `spawn_blocking` только для больших текстов, адаптивный допуск → 429 (§12.1), HTTP/1.1 keep-alive.

Ожидание: типичное предложение (100–300 символов) — < 100 мкс CPU в ядре, текст 100k токенов (~400 КБ) — десятки миллисекунд.

План замеров (войдут в README): `oha`/`k6` по протоколу проверки (пары mask→demask, ретраи, учёт 429) на 1 000, 2 000 и 10 000 RPS × 5 минут; таблица p50/p95/p99, доля 429, CPU/RAM на реплику; отдельный прогон на тексте 100k токенов; `criterion`-бенчмарки ядра.

## 18. Ограничения и план развития

- Детекция ФИО опирается на словари и морфологические эвристики: редкие/иностранные имена без контекста могут быть пропущены; план — опциональный NER-плагин (ONNX, `ort`) как ещё один `Detector` с бюджетом времени и включением per-system.
- Границы «органа, выдавшего паспорт» и свободных адресов — эвристические; план — грамматика на основе ФИАС/справочников и обучение на размеченных данных банка.
- Даты, написанные полностью словами («двенадцатого мая тысяча…»), покрываются ограниченно.
- Стриминг ответа LLM демаскируется с буферизацией — задержка первого токена растёт на длину самого длинного плейсхолдера.
- Демаскирование ответа LLM при позиционных масках (`45** ****56`) неоднозначно при коллизиях — для LLM-сценариев рекомендуем профиль `placeholder`.

## 20. Принятые решения и открытые вопросы

Решено (обсуждение 2026-09-22):
- Язык и стек: Rust (axum/tokio, regex, aho-corasick). Развёртывание — Kubernetes, несколько реплик → Redis как общее хранилище соответствий, память — L1-кэш после подтверждённой записи; ошибка Redis отдаётся вызывающему (`429 STORE_BUSY` на `/process`), а не скрывается памятью (уточнено 2026-09-23).
- «Слабые» сущности (голая дата, город без адреса, одиночное имя) по умолчанию маскируются **только при контексте или комбинации**; режим «маскировать всегда» доступен в конфиге.
- Стриминг SSE в LLM-прокси — после ядра; первая версия прокси — без стриминга.
- В scope демо: Web UI, OpenAI-совместимый прокси, дашборд (Grafana локально, Monium в облаке), нагрузочный сценарий с отчётом.

Закрыто после прогона `scripts/probe_reference.sh` с внешней машины:
1. **Эталонный вид маски по типам.** Эталонный эндпоинт организаторов (`process-test.holydev.space/process`) — заглушка: возвращает `payload` без изменений на обоих шагах и демонстрирует только формат обмена, как и сказано в онбординге. Внешнего образца маски нет; профиль `reference` выведен из единственного свидетельства — примера контракта (`И. И. И.`, `45** ****56`) — и анализа метрики (span-Левенштейн): см. README, раздел «Профили маскирования».
