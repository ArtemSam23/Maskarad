# Нагрузочное тестирование

Сценарий `load/k6-process.js` воспроизводит протокол проверяющей системы (ТЗ, прил. B): пары
`POST /process` — маскирование и демаскирование с одним `payload_id`, до 3 попыток на запрос, при `429`
ожидание `Retry-After`, таймаут 10 с, восстановленный текст сравнивается с исходным. Интенсивность
задаётся в парах в секунду (500 пар/с = 1 000 запросов/с), поток открытый (arrival rate): если сервер
замедлился, генератор не подстраивается, а копит `dropped_iterations`. Параллельно можно включить поток
больших текстов (1×/4×/8×/16× корпуса, ≈ 14k–236k токенов) — он информационный, в вердикт не входит.

Результаты и методика замеров — `docs/performance.md`. Прогон на проде делается одной кнопкой из облака:
Actions → ops → `loadtest`.

## Из облака (Actions → ops → loadtest)

Workflow `.github/workflows/ops.yml`, действие `loadtest`. Что происходит:

1. Образ `ghcr.io/grafana/k6:<k6_version>` зеркалируется в `cr.yandex/<registry>/k6` (узлы кластера тянут
   ghcr.io ненадёжно).
2. Создаётся временная группа узлов `loadgen` (1 × standard-v3, 8 vCPU / 16 ГБ, network-hdd, taint
   `role=loadgen`, версия Kubernetes — как у мастера) в подсети рабочих узлов. Группы нет в Terraform:
   она живёт только на время прогона. Узел помечен
   `node.kubernetes.io/exclude-from-external-load-balancers=true`, и workflow проверяет по target group
   балансировщика ingress, что узла там нет: с `externalTrafficPolicy: Cluster` часть соединений иначе
   шла бы через сам генератор. Если группа осталась от прошлого прогона — используется как есть; если
   она ещё удаляется — workflow ждёт, пока исчезнет, и создаёт заново.
3. Корпус собирается из `tests/golden/*.jsonl`, сценарий и данные кладутся в ConfigMap `loadtest-scenario`
   в namespace `loadtest`; Job `k6-<run_id>` запускается на узле `loadgen` в host network (privileged
   initContainer поднимает conntrack и диапазон портов узла) и ходит на `url` через публичный адрес
   балансировщика — тот же путь, что у проверяющей.
4. В summary запуска: клиентские итоги k6, серверный отчёт `scripts/loadtest_report.sh` по метрикам из
   Monium (воркспейс Managed Prometheus) за окно прогона (окно берётся из сводки k6: `run_start_ms`/`run_end_ms`, без
   планирования пода и init VU) и вердикт. Полный лог k6, JSON-сводка, серверный отчёт и `server.kv` —
   в artifact `loadtest-<run_id>-<attempt>`.

Параметры: `rps` (пар/с, по умолчанию 500), `duration` (5m), `stages` (если задано — ступени вместо
rps/duration, например `3m:500,2m:750,3m:750`), `keepalive` (off — новое TLS-соединение на каждый запрос),
`big_per_10s` (больших пар за 10 с, 0 — без них), `url`, `keep_loadgen`, `k6_version`. Это все десять
inputs, которые допускает `workflow_dispatch`; новый параметр — только объединением существующих.

Ступени линейные: каждая ведёт интенсивность от предыдущей цели к своей, первая начинается со своей
цели. Полка после роста — повтор цели (`2m:750,3m:750`).

### Вердикт

PASS, если одновременно:

- невалидных ответов (не 200 и не 429) нет; несовпадений демаскирования нет; пар, не завершённых за
  3 попытки, нет;
- доля `429` не больше 1 % запросов. Проверяющая ретраит `429` по `Retry-After`, но заметная доля
  сброшенной нагрузки значит, что сервис не тянет, а не что лимит настроен;
- ответов по HTTP/1.1 не меньше 99.9 %. Единственная защита от h2 в Job — `GODEBUG=http2client=0`,
  новая версия k6 может её молча снять, а без keep-alive h2 скрыл бы цену TLS-рукопожатий;
- ingress p99 по `status="200"` за окно < 0.5 с (гистограмма nginx по хосту; `429` отвечаются
  мгновенно и тянули бы общий p99 вниз, поэтому гейт — по успешным ответам; p99 по всем статусам
  рядом, справочно);
- выполнено ≥ 95 % пар от плана, `dropped_iterations` < 0.1 % итераций.

FAIL по любому пункту — job красный, прогон работает как гейт. Если серверного отчёта нет
(`YC_PROMETHEUS_WORKSPACE_ID` не задан, API воркспейса не ответил, за окно нет данных) — вердикт
**НЕПОЛНЫЙ** и тоже exit 1: клиентский p99 печатается справочно, но гейт по latency он не заменяет.
Отдельно проверяется, что серверный отчёт видел запросы `mask` (`service_mask_p99_s` в `server.kv`):
если их нет, прогон мерил только demask — см. правило про TAG ниже. Большие тексты и рестарты подов
(kubectl, разница `restartCount` до и после) — справочно.

### TAG и payload_id

`payload_id` строится из TAG (`gh-<run_id>-<run_attempt>` в облаке, `TAG` в переменных локально).
Соответствия живут в хранилище 3600 с: если TAG повторить в пределах часа, сервис примет запрос за
повторный, уйдёт в ветку demask и вернёт ответ по сохранённому соответствию, не маскируя. Такой прогон
меряет не то, и вердикт помечает его НЕПОЛНЫМ. Локально задавайте `TAG=local-$(date +%s)`.

### Узел loadgen: стоимость и удаление

Cleanup удаляет группу `loadgen` всегда, кроме `keep_loadgen=true` (для серии прогонов). Узел
standard-v3 8 vCPU / 16 ГБ стоит порядка 13–14 ₽/ч (≈ 1.24 ₽/ч за vCPU плюс память, тарифы Compute,
сентябрь 2026) — оставленная группа за сутки съедает ~320 ₽. Удалить вручную:

```bash
yc managed-kubernetes node-group delete --cluster-name maskarad --name loadgen
```

### Без keep-alive: conntrack рабочих узлов

Каждый запрос без keep-alive — новое соединение, а запись conntrack о нём живёт ещё 120 с после закрытия
(TIME_WAIT). Таблица conntrack узла — 131 072 записи, то есть заполняется при ~1 100 новых соединений/с
на узел; при четырёх узлах и балансировщике это ~4 000 запросов/с суммарно, а на одном узле «table full,
dropping packet» начинается уже около 1 000 rps без keep-alive. Выше этой отметки результаты говорят про
conntrack узлов, а не про сервис. В Managed Kubernetes параметры conntrack у kube-proxy не настраиваются;
поднимать `net.netfilter.nf_conntrack_max` и `nf_conntrack_tcp_timeout_time_wait` на рабочих узлах
нужно privileged DaemonSet'ом (в репозитории его нет). На самом генераторе это делает initContainer Job'а.

## Локально

Нужны docker и jq. Образ k6 — `ghcr.io/grafana/k6`. Корпус и большой текст генерируются из golden-датасета
(в репозиторий не кладутся, см. `load/.gitignore`):

```bash
jq -c -n '[inputs | {text: .text}]' tests/golden/*.jsonl > load/corpus.json      # 1141 текст, 130 КБ
jq -r '.text' tests/golden/generated.jsonl | tr '\n' ' ' > load/bigtext.txt      # 73k символов, база для 1×–16×
```

Полка 500 пар/с 5 минут против прода:

```bash
docker run --rm -v "$PWD/load:/w:ro" -w /w \
  -e URL=https://maskarad.tech -e STAGES=5m:500 -e TAG=local-$(date +%s) \
  ghcr.io/grafana/k6:1.3.0 run --summary-trend-stats "avg,min,med,p(90),p(95),p(99),p(99.9),max" k6-process.js
```

Переменные: `URL`, `STAGES` (`5m:500`; формат `длительность:пар/с[,...]`), `KEEPALIVE` (`1`|`0`),
`BIG_PER_10S` (`0`), `TAG` (часть `payload_id` и User-Agent; уникальная метка на прогон, см. выше),
`LOG_MISMATCH=1` (лог первых несовпадений), `PREVUS`/`MAXVUS` (по умолчанию пиковая цель ×1 и ×4, не
больше 6000), `CORPUS_PATH`, `BIGTEXT_PATH`. Без keep-alive нужен диапазон портов пошире:
`--sysctl net.ipv4.ip_local_port_range="1024 65535"` у `docker run`.

Замеры с ноутбука через интернет годятся до ~2 000 запросов/с: выше генератор упирается в число VU и в NAT
Docker Desktop, и клиентские хвосты latency перестают говорить о сервере. Для цифр — прогон из облака.

Серверный отчёт за окно прогона (unix-секунды): против прода — из воркспейса Prometheus в Monium
(`YC_PROMETHEUS_WORKSPACE_ID`, токен берётся из настроенного `yc`); для локального стенда
`deploy/docker-compose.yml` — из его Prometheus на `localhost:9090` через `PROM_URL` (там нет
ingress-nginx и cAdvisor, эти таблицы будут пустыми):

```bash
YC_PROMETHEUS_WORKSPACE_ID=<id> scripts/loadtest_report.sh <start> <end> "my run" --stages "3m:500,2m:750"
PROM_URL=http://127.0.0.1:9090 scripts/loadtest_report.sh <start> <end> "local run"
```

Окно проще всего взять из сводки k6: `run_start_ms`/`run_end_ms` между `===K6_SUMMARY_BEGIN===` и
`===K6_SUMMARY_END===` в выводе, делённые на 1000.

## Как читать отчёт

Клиентская часть (k6): `invalid_responses` — ответы не 200 и не 429 (5xx, обрыв, таймаут); пять таких подряд
останавливают прогон проверяющей, поэтому норма — ноль. `demask_mismatch` — восстановленный текст не равен
исходному: штраф по точности без видимой ошибки. `mask_latency` / `demask_latency` — первая попытка запроса;
таймаут в неё входит как 10 000 мс (иначе самые медленные запросы выпадали бы из p99), обрыв соединения —
не входит. `pair_latency` — вся пара с ретраями. `rate_limited` и `retries` — сколько раз сервер отвечал 429
и сколько было повторов. `dropped_iterations` — генератору не хватило VU, фактическая интенсивность ниже
плана: такие хвосты latency — очередь в k6, а не сервер. `proto_http1` — доля ответов по HTTP/1.1 (как у
проверяющей на Python). `actual_rps` считается по плановой длительности: фактическая включает
gracefulStop без новых итераций. У большого потока свои `big_*` счётчики (невалидные, таймауты, 429,
ретраи, незавершённые пары, первые попытки дольше 10 с) — они не смешиваются с основным потоком.

Серверная часть (воркспейс Prometheus в Monium, `prometheus-agent`): ingress p50/p95/p99 — гистограмма nginx по хосту,
отдельно по всем статусам и по `status=200` (гейт); сервис p99/p99.9 по направлениям — гистограмма
обработчика `/process`; `store errors` — ошибки Valkey (таймауты 200 мс), при них сервис отдаёт маску
вместо оригинала; CPU и память подов сервиса и ingress, CPU и память узлов — из cAdvisor kubelet'ов
(корневой cgroup); реплики min/max — по числу целей скрейпа `up{job="maskarad"}`. Таблица по ступеням
есть, если прогон шёл со `stages`. Любой неудавшийся запрос к воркспейсу — «(ошибка)» в ячейке и exit 1,
чтобы пустую таблицу не приняли за «всё по нулям».

## `maskarad bench`

Встроенный генератор (HTTP/1.1, keep-alive, тот же протокол пар) — для замера ядра на одной машине и
контрольного прогона Job'ом внутри кластера (`scripts/k8s_job.sh`, см. `cd.yml`). Больших текстов и режима
без keep-alive в нём нет.

```bash
maskarad bench --url http://localhost:8080 --rps 1000 --duration 60 --dataset tests/golden
```
